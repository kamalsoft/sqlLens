# API Reference

All routes are local-only (D-008). Every route except `POST /api/auth/login` needs a signed-in session cookie (`session_token`, HttpOnly, SameSite=Lax, `Secure` in production, 7-day lifetime; the database stores only its SHA-256, SEC-T6) and returns 401 without one. `src/proxy.ts` runs before every `/api/*` request: the `Host` header must be `localhost`, `127.0.0.1`, `[::1]` or a name in `SQLLENS_ALLOWED_HOSTS` (403 otherwise, against DNS rebinding), and a POST, PUT, PATCH or DELETE whose `Origin` is a different host, or that a browser marks `Sec-Fetch-Site: cross-site`, is rejected (403, CSRF). Rate limits are per session, in memory, and reset on restart: execute and catalog routes 10/min, review 5/min, downloads 5/min, settings save 10/min, share create/revoke 20/min, feedback 60/min, record delete 30/min (SEC-T7). Login: 5/min per username and 20/min overall, plus 5/min per client address when `SQLLENS_TRUST_PROXY=1`. Every response carries `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Permissions-Policy` (SEC-T3, `next.config.ts`).

## `POST /api/review`

Request:

```json
{
  "modelId": "owner/model",
  "sql": "CREATE PROCEDURE dbo.Test AS SELECT 1;"
}
```

`sql` is required. RV-1: `modelId` is optional; without it the route uses `reviewModel` from Settings, or (empty, or no longer installed) the same automatic choice as Refactor (chat template, then instruction-tuned name, then size); 404 when no compatible model is installed. `schemaVersion` is optional; without it `reviewSchema` from Settings applies (`auto`: v1 for small models, v2 otherwise). `executionAuditId` (optional) is one of the session's own EXECUTE or EXECUTE_COMPARE records; RV-3: it works with any schema (the telemetry prompt asks for v2 and a v1 answer is accepted with `schemaFallback`). RV-2: reviews are findings only; `rewrittenProcedure` is always `""` and `rewriteNotes` `[]`, a rewrite the model adds anyway is discarded, and Refactor makes rewrites. `sql` is trimmed before use (`src/app/api/review/route.ts:194`). Planned: P1-06 adds input length and NUL-byte validation.

Success response (`200`): `{ "id", "recordNumber", "model", "schemaVersion", "lowConfidence", "schemaFallback"?, "promptPath", "executionAuditId"?, "result" }`; the review is saved as a REVIEW audit record with the prompt that was sent.

Status codes:

- `200`: analysis completed (`route.ts:270`).
- `400`: `sql` is missing, or `modelId` is not a non-empty string .
- `404`: the model is not installed (`route.ts:206-210`).
- `422`: the model is installed but not compatible with local Transformers.js (`route.ts:213-220`).
- `502`: the model returned no text (`route.ts:258-264`), or its output could not be parsed as JSON; the body includes a `details` object (`route.ts:276-289`).
- `500`: unexpected server error (`route.ts:294-302`).

## Review and model route behavior (P6-03c, P3-02, P3-06)

All `/api/review/**` and `/api/models/**` handlers require a session (401). `POST /api/review` is limited to 5 requests per minute per session and `POST /api/models/download` to 5 per minute (429). Review errors: 400 (invalid SQL, text that does not look like SQL — `looksLikeSql` in `src/lib/validation/sql-input.ts` requires a recognisable statement such as `CREATE PROCEDURE`, `SELECT … FROM`, `SET NOCOUNT`, `EXEC schema.proc`; `/api/compare` applies the same check to `original` and `optimized` —, `schemaVersion`, or prompt larger than the context window), 404 (model not installed), 422 (incompatible model), 429 (rate limit, or another inference is running), 502 (model output is not valid JSON for the schema; when the outer JSON object never closes and the new-token budget was used up, the error names the `maxNewTokens` limit (or says the model was repeating itself when the output loops); when the model stopped on its own with only a final string value open, that string is closed and the review is validated normally; `details.responseText` carries the raw output, up to 50,000 characters), 504 (inference exceeded `inferenceTimeoutMs`; raise it in Settings or shorten the SQL). 500 returns `{ "error": "Internal error" }`. For v2 results, rows in `findingsTable`, `performanceTable` and `securityTable` whose `evidence` is not quoted from the submitted SQL (whitespace and case ignored; `"not observed"` is kept) are removed, and a `limitations` entry states how many. RV-2: reviews are findings only. A `<rewritten_procedure>` block or `rewrittenProcedure` value the model still writes is discarded: the result always has `rewrittenProcedure: ""`, `rewriteNotes: []` and no `rewriteStatus`/`rewriteDetail` (older audit records keep theirs and still render them). When the new-token limit cuts off an old-style answer inside its final `rewrittenProcedure` string, the findings are still recovered. Missing commas between array items or objects are repaired. In v2, a malformed table row is dropped and counted in `limitations` instead of failing the review; enum values are normalised (`"Error Handling"` → `error_handling`), missing tables default to `[]`, and evidence abbreviated with `...` is kept when every fragment appears in the SQL in order. For index rows, every column must be qualified with that table's alias or name, or used unqualified without being an `AS` alias; comments are ignored. Both schema versions include `indexRecommendations` (`[]` when absent): each row has `table`, `keyColumns`, `includeColumns`, `reason`, `evidence`. The route keeps a row only when the table is referenced after `FROM`/`JOIN`/`UPDATE`/`INTO`/`MERGE` (not an alias, CTE, `#temp` or `@table`) and every column appears in the submitted SQL, then adds a server-generated `createStatement` (`CREATE NONCLUSTERED INDEX …`, identifiers bracket-escaped); model-written DDL is never returned. At most 5 rows, 6 key and 10 include columns; for v2, a `limitations` entry counts removed rows. When `schemaVersion` is omitted, `reviewSchema` from Settings applies; on `auto`, `small` models use `v1` (D-035) and others use `v2`. An explicit `schemaVersion` wins. With `executionAuditId` the telemetry prompt is used and v2 is requested whatever the setting (RV-3). The review response includes `lowConfidence: boolean` (true for small models). If a `v2` request (with or without telemetry) returns valid `v1` JSON, the review is accepted as `schemaVersion: "v1"` with `schemaFallback: true` and `lowConfidence: true`. There is no mock fallback. `SQLLENS_FAKE_INFERENCE=1` returns canned JSON outside production only.

## Audit storage note (D-028 scope)

The SQLite audit record written for an execution stores the batch SQL text regardless of the `logSqlText` setting. `logSqlText=false` only omits the SQL from the on-disk text audit log (a SHA-256 and length are written instead). Treat the SQLite audit database as containing submitted SQL.

## Review persistence and telemetry (P4-01)

`POST /api/review` persists each successful result as a `REVIEW` audit (`schema_version`, `model_id`) and returns its `id` and `recordNumber`. Optional `executionAuditId` (the caller's own EXECUTE/EXECUTE_COMPARE audit; 404 otherwise; requires `schemaVersion` v2) injects normalized telemetry (no raw output) using `data/prompts/review-with-telemetry.md`; the response echoes `executionAuditId`.

`POST /api/models/download` only deletes directories that resolve inside the configured download root; an unsafe `modelId` returns 400.

## Repeated runs (P8-03)

Repeated runs: an optional `runs` (integer, 1 to `maxRuns`) asks for that many measured runs; above 1 a warm-up run is added first and dropped from the summary (`result.analysis.multiRun`). Without `runs`, a single-mode request on a real engine uses `measuredRuns` from the config (default 2, so 3 executions); simulation and compare requests run once. `runs` above 1 in compare mode is a 400. If the warm-up or a middle run fails, the remaining runs are skipped; that run writes no audit log file, and the audit record stores the error.

## MSSQL batch restrictions (D-034)

In MSSQL batch mode the request is rejected with 400 if the SQL (after comments and quoted text are masked) contains `EXEC`, `EXECUTE` or `sp_executesql` (including `EXEC(` and `[sp_executesql]`): "use procedure mode to run procedures". `COMMIT`, `ROLLBACK` and `BEGIN`/`END` are allowed and run as written (D-036). A batch runs inside one transaction that is rolled back at the end, unless the script commits. Lines holding only `GO` split the MSSQL script into separate batches, as in SSMS, all in that transaction. Procedure mode is unchanged. Each execution's `analysis.prodVerdict` is `{ verdict, reason, driver }` (P8-02; targets in `docs/configuration.md`). A single-mode request may set `runs` (P8-03, 1 to `maxRuns`): one warm-up run plus `runs` measured runs, with `analysis.multiRun` holding median, p95 and spread; only the last run is written to the audit log, and a failing run stops the sequence. `analysis.planFindings` (P8-07) lists generic plan findings: cost concentration (one operator holds at least 50% of logical reads), row estimate far from the actual rows per execution (10x or more, at least 1,000 rows), and tempdb spills. Each finding names the operator type and the object the plan reports; nothing is keyed to specific names. Procedure parameters may set `"output": true` (MSSQL only; PostgreSQL returns 400): the procedure's OUTPUT value is returned in `outputs` on the execution result and written to the audit log. Pass `value: null` for an OUTPUT parameter.
